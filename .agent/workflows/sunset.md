# /sunset - システム非推奨化と移行

コードは資産ではなく負債です。「安全に削除すること」は「作ること」と同じくらい重要なプロダクトエンジニアリングです。

## 🎯 目的
メンテナンスされていないZombie Codeや、古くなったアーキテクチャの依存を断ち切り、システム全体をクリーンに保つ。

## 🔄 実行プロセス

### Step 1: 依存関係と影響の可視化
- `grep_search` による参照元（`use` 等）の物理波及分析と、`.context/RIPPLE_MAP.md` による意味依存分析を使用し、非推奨対象を利用しているすべてのコンシューマを特定する。
- 完全に使われていない Zombie Code （6ヶ月以上更新がなく、メンテナ不在のもの）かどうかを確認する。
// turbo
```bash
# Zombie Code スキャンの例 (対象ディレクトリ内の古いファイルの洗い出し)
git log --since="6 months ago" -- <対象パス>
```

### Step 2: 代替手段の提供と移行戦略
機能削除のみの場合を除き、対象を「Advisory (任意)」か「Compulsory (強制)」のどちらで非推奨にするか決定し、戦略を練る。

| 連携パターン | Rust 実装例 | 目的 |
|-----------|-----------|------|
| **Strangler** | `routes` スプリッティング（トラフィック割合で旧実装へフォールバック） | エンドユーザー影響の最小化 |
| **Adapter** | `impl OldTrait for NewStruct { ... }` | 既存の呼び出し側コードを変えずに裏側のみを刷新 |
| **Feature Flag** | `if ctx.has_flag("use_new_engine") { ... }` | コンシューマごとの動的なオン/オフ切り替え |

### Step 3: CHANGELOG と ADR への記録
非推奨化・削除の根拠や方針を決定した場合は、必ず `CHANGELOG.md` に `[Deprecated]` または `[Removed]` として記載し、設計変更を伴う場合は `docs/decisions/` にADRを追加する。

### Step 4: インクリメンタルな移行
コンシューマを一度にすべてではなく、1つずつ安全に移行し、都度テストを実行する。
// turbo-all
```bash
cargo check --workspace --tests && (cd apps/management-console && npm run lint)
```

### Step 5: 古いシステムの完全削除
100%のトラフィックが新システムへ移行されたことを確認した後、古いコード、テスト、ドキュメントの参照、非推奨警告を完全に削除する。

## 🛑 共通の言い訳 (Anti-rationalization)

| エージェント(AI)のよくある言い訳 | 現実 (Reality) |
|----------------------|----------------|
| 「まだ動いているのに、なぜ消すのですか？」 | 誰もメンテしないコードはセキュリティリスクと複雑性をサイレントに増大させます。 |
| 「後で誰かが必要とするかもしれません」 | 必要になったら再構築できます。「念のため」に保持するコストの方が高くつきます（YAGNI）。 |
| 「移行コストが高すぎます」 | 2〜3年のメンテナンスコストと比較してください。大抵の場合、今移行する方が安上がりです。 |
| 「新しいシステムが完成してから非推奨化を計画します」 | 非推奨計画は設計時に始まります。新システムが完成する頃には別の優先事項にとらわれます。 |
| 「ユーザーは勝手に移行してくれるはずです」 | ユーザーは既存の暗黙の振る舞いに依存しています(Hyrum's Law)。自動移行の案内を提供してください。 |
| 「新旧両方を永遠に維持すれば安全です」 | 同等の処理を2つ維持することは、テスト負荷やオンボーディングの混乱を倍増させます。 |

## ✅ 最終チェック
- [ ] 新機能/代替システムが本番想定で実装・テストされている
- [ ] すべてのコンシューマが移行済みであり、旧処理への依存が残っていない
- [ ] 古いシステムに関する死んだ型定義やDocsが完全に削除されている
