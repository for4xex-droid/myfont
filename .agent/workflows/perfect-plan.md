# /perfect-plan パーフェクトプランニング 🎯

計画書（implementation_plan.md 等）に対して、**5つの異なる視座**から抜け漏れを徹底検証するメタワークフローです。
個別ワークフロー（`/brainstorm`, `/deep-scan`, `/red-team`, `/preflight`）の強みを1つのパイプラインに統合しています。

## いつ使うか
- 新しいフェーズの実装計画を立てた**直後**
- 大きなアーキテクチャ変更の**着手前**
- 「何か見落としてないか？」と不安になった時

---

## 実行手順

### Gate 1: 📡 構造スキャン

`ARCHITECTURE.md`（リポジトリルート）を読み込み、**計画に記載された変更対象（構造体・エンドポイント・コンポーネント）が実際のコードベースに存在するか**を確認する。

チェック項目：
- [ ] 計画で「新規作成」とされたモジュールが、既に別名で存在していないか？（二重実装の防止）
- [ ] 計画で「修正」とされたファイルが、アーキテクチャ定義上に実在するか？（幻覚の排除）
- [ ] 計画に登場しない既存モジュールで、影響を受けるものがないか？（波及漏れ）

### Gate 2: 📋 要件カバレッジ検証（NURTURE クロスチェック）
計画をNURTURE要件定義書（9セクション）と突き合わせ、**カバーされていない要件**を洗い出す。

チェック項目：
- [ ] §2 経済台帳 — 計画はトランザクションや通貨に影響するか？
- [ ] §3 MCP統合 — 計画は新しいツールやMCPエンドポイントを追加するか？
- [ ] §4 セキュリティ — 計画は認証・認可・入力検証に影響するか？
- [ ] §5 法的リスク — 計画はCSAM・ダークパターン・コンプライアンスに触れるか？
- [ ] §6 VRM/3D — 計画はレンダリングやアセットに影響するか？
- [ ] §7 A2C — 計画はユーザーへの報酬・ギフトに関連するか？
- [ ] §8 P2P Hub — 計画はFederation/CRDT同期に影響するか？

### Gate 3: 🔗 依存関係 & 波及分析
`grep_search` による参照箇所（`use` 等）の物理走査結果と、`.context/RIPPLE_MAP.md` の意味的依存関係から、計画で変更するファイルの**全ての依存先**を洗い出す。

チェック項目：
- [ ] 変更する構造体を `use` している全ファイルが計画に含まれているか？
- [ ] テスト用のMock（`MockJobQueue` 等）にも影響が波及しないか？
- [ ] `api_integration_tests.rs` への影響はないか？

### Gate 4: 😈 悪魔の弁護人（Red Team 思考実験）
計画に対して、**意地悪な質問を3つ**投げかける。

1. **最悪のシナリオ**: この計画が最も壊滅的に失敗するとしたら、何が原因か？
2. **見落とされた前提**: この計画が暗黙に前提としている仮定で、実は正しくないものは何か？
3. **やらない方がいい**: この計画を「実行しない」という選択肢に、メリットはないか？

### Gate 5: ⏱️ 実行順序 & タイミング検証
計画内のステップの**実行順序**に論理的な矛盾がないかを検証する。

チェック項目：
- [ ] Step N が Step M に依存しているのに、M が N より後に来ていないか？
- [ ] 並列実行可能なステップが無駄に直列化されていないか？
- [ ] 既知の残存ギャップ（`OPEN.md` / `TECH_DEBT_AUDIT.md` 記載の tech debt）が、この計画の前提を壊さないか？

## 出力フォーマット

```markdown
# パーフェクトプランニング検証結果

## 検証対象
[計画名 / ファイルパス]

## Gate 1: 構造スキャン
- ✅ / ⚠️ [結果]

## Gate 2: 要件カバレッジ
- ✅ / ⚠️ [結果]

## Gate 3: 依存関係
- ✅ / ⚠️ [結果]

## Gate 4: 悪魔の弁護人
1. [最悪のシナリオ]
2. [見落とされた前提]
3. [やらないメリット]

## Gate 5: 実行順序
- ✅ / ⚠️ [結果]

## 判定
- [ ] ✅ PASS — 計画は堅牢。実行に移してOK。
- [ ] ⚠️ PATCH — 軽微な修正後に実行可能。
- [ ] 🔴 REJECT — 計画の根本的な見直しが必要。
```
