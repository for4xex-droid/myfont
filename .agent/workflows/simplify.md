# /simplify - コード簡素化

コードの「振る舞い」を一切変えずに、「可読性・保守性」のみを向上させるための厳密なリファクタリングワークフロー。

## 🎯 目的
コードベースから不要な複雑さ、重複、過剰な抽象化を取り除き、次世代のAIエージェントや人間のエンジニアが保守しやすい状態にする。

## 🔄 実行プロセス

### Step 1: Chesterton's Fence (意図の確認)
削除または簡略化する前に、現在の実装理由を必ず理解する。
- ターミナルで `git blame <file> -L <start>,<end>` を実行し、変更のコンテキスト（過去のバグ修正やエッジケース対応など）を確認する。
- 理由がわからない場合は削除・変更しない。

### Step 2: 複雑性の特定
以下のシグナルを探す:
- 深いネスト (3階層以上)
- 巨大な関数 (50行以上)
- 複雑な三項演算子のネスト
- 重複するロジック (5行以上のコードブロック)
- `data`, `result` といった汎用すぎる命名や、実態と乖離した命名

### Step 3: 変更の適用とGolden Rules照合
- **500行ルール**: 変更箇所が500行を超える見込みの場合は、手作業を避け codemod やスクリプトでの自動化を検討する。
- **Golden Rules クロスチェック**:
  - D-001: 簡略化の結果、安全なエラーハンドリングが `unwrap()` に置換されていないか？
  - U-002: UI変更を含む場合、ハードコードされた色が混入していないか？

### Step 4: 漸進的検証 (Incremental Verification)
1回の論理的な変更ごとにビルドとテストを実行する。
// turbo-all
```bash
cargo check --workspace --tests && (cd apps/management-console && npm run lint)
```
テストが通らない場合は即座にrevertし、別のアプローチを検討する。

## 🛑 共通の言い訳 (Anti-rationalization)

| エージェント(AI)のよくある言い訳 | 現実 (Reality) |
|----------------------|----------------|
| 「動いているので、触る必要はありません」 | 読みにくいコードは壊れた時に直せません。今シンプルにすることで未来の時間を救います。 |
| 「行数が少ない方が常にシンプルです」 | 1行に圧縮された三項演算子より、5行の if/else の方が可読性が高いです。行数より認知負荷を下げてください。 |
| 「ついでに関係ないところも綺麗にしておきます」 | スコープ外の変更はdiffを汚し、デグレのリスクを生みます。今フォーカスしている場所だけに集中してください。 |
| 「型付けがあるので自己文書化されています」 | 型は構造を示しますが「意図」は示しません。適切な変数名/関数名でWhyを語ってください。 |
| 「この抽象化は後で役に立つかもしれません」 | 推測による抽象化は有害です（YAGNI）。今使われていないなら削除し、必要になった時に再度追加してください。 |
| 「元の作者には何か理由があったはずです」 | かもしれません。`git blame`で意図を確認してください。しかし、単にプレッシャー下で積まれた負債であることも多いです。 |
| 「新機能を追加しながらリファクタリングします」 | リファクタリングと機能追加は混ぜないでください。両方を同時に行うと切り分けやレビューが困難になります。 |

## ✅ 最終チェック
- [ ] 既存のテストがすべて「無修正」でパスしている
- [ ] 例外処理やエッジケースのハンドリングが削られていない
- [ ] 使用されていない import やデッドコードが残っていない
