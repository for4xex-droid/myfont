# /code-review - コードレビューコマンド

コードの品質、セキュリティ、保守性を多角的に分析します。

## レビュー観点

### 1. セキュリティ 🔒
- [ ] ハードコードされた秘密情報がないか
- [ ] SQLインジェクション対策
- [ ] XSS対策
- [ ] 入力バリデーション
- [ ] 認証・認可の適切な実装

### 2. コード品質 ✨
- [ ] DRY原則（重複コードなし）
- [ ] 単一責任の原則
- [ ] 適切な命名
- [ ] コメントの適切性
- [ ] 関数の長さ（50行以内推奨）

### 3. パフォーマンス ⚡
- [ ] N+1クエリの回避
- [ ] 適切なインデックス使用
- [ ] メモリリークの可能性
- [ ] 不要な再レンダリング（React）
- [ ] キャッシュの活用

### 4. 保守性 🔧
- [ ] テストの存在
- [ ] ドキュメントの更新
- [ ] 型定義の適切性
- [ ] エラーハンドリング
- [ ] ログ出力

### 5. Change Size ガイドライン 📏
- Google推奨: 1回のPR/レビューは200行以内。
- 巨大な差分(500行以上)は認知負荷が高まり、見落としが発生します。分割を提案してください。

## レビュー実行手順

### ステップ1: 変更ファイルの確認
```bash
git diff --name-only HEAD~1
```

### ステップ2: 総合レビューレポートの出力

以下の2つの形式でアーティファクトを出力します。

#### 1. Markdown サマリー
簡易的な指摘事項と全体スコアを記述。

#### 2. リッチ HTML レポート
`code_review_report.html` という名前で、以下の要素を含む HTML を生成してください。
- **シンタックスハイライト済みの差分**: 指摘箇所をコード内で直接ハイライト。
- **重大度に応じたカラーコード**:
    - 🔴 **High**: `var(--status-error)`
    - 🟡 **Medium**: `var(--status-warning)`
    - 🟢 **Low/Safe**: `var(--status-success)`
- **折りたたみ可能なセクション**: ファイルごとのレビュー詳細をインタラクティブに開閉。
- **修正案のワンクリックコピー**: 提案コードをコピーしやすくするためのボタン（CSS/JS）を配置。

ファイルごとのレビューは以下の形式で記述します。

```markdown
## [ファイル名] レビュー

### セキュリティ
- ✅ 問題なし / ⚠️ 要修正: [詳細]

### コード品質
- ✅ 問題なし / ⚠️ 要修正: [詳細]

### パフォーマンス
- ✅ 問題なし / ⚠️ 要修正: [詳細]

### 保守性
- ✅ 問題なし / ⚠️ 要修正: [詳細]
```

### ステップ3: レビュー結果サマリー

```markdown
# コードレビュー結果

## 概要
- レビュー対象: X ファイル
- 問題点: Y 件（クリティカル: A, 警告: B, 情報: C）

## クリティカル問題 🔴
1. [ファイル:行] - [問題の説明]
   - 推奨修正: [修正方法]

## 警告 🟡
1. [ファイル:行] - [問題の説明]
   - 推奨修正: [修正方法]

## 情報 🔵
1. [ファイル:行] - [改善提案]

## 良い点 ✨
- [良かった実装の説明]

## 結論
[ ] 承認 - マージ可能
[ ] 要修正 - 上記問題を修正後に再レビュー
[ ] 却下 - アプローチの再検討が必要
```

## セキュリティチェックリスト詳細

### 認証・認可
```typescript
// ✅ Good
const user = await auth.verifyToken(token);
if (!user.hasPermission('admin')) {
  throw new ForbiddenError();
}

// ❌ Bad
if (req.query.isAdmin === 'true') {
  // 管理者処理
}
```

### 入力バリデーション
```typescript
// ✅ Good - Zodによるバリデーション
const schema = z.object({
  email: z.string().email(),
  age: z.number().min(0).max(150)
});

// ❌ Bad
const email = req.body.email; // 未検証
```

### SQLインジェクション
```typescript
// ✅ Good - パラメータ化クエリ
await db.query('SELECT * FROM users WHERE id = $1', [userId]);

// ❌ Bad - 文字列連結
await db.query(`SELECT * FROM users WHERE id = ${userId}`);
```

## 🛡️ Reviewer Integrity (品質への妥協禁止)
レビュイー（コード作成者）の感情に配慮することは重要ですが、品質基準を下げる理由にはなりません。
問題を見つけた場合は「良い試みですが...」と前置きしつつ、**必ず修正を要求**してください。

## 🛑 共通の言い訳 (Anti-rationalization)

| エージェント(AI)のよくある言い訳 | 現実 (Reality) |
|----------------------|----------------|
| 「この変更は小さいからレビュー不要です」 | 1行の変更でもシステムを破壊できます。依存関係やロジック反転を見落とさないでください。 |
| 「動作確認済みなので大丈夫です」 | "It works" は最低要件に過ぎません。"It's maintainable" と "It's secure" を確認するのがレビューです。 |
| 「緊急対応なので多少の汚さは許容します」 | 緊急対応ほどバグが混入しやすいです。少なくとも安全を担保するテストは必須としてください。 |
| 「複雑なロジックなので仕方ありません」 | 複雑なロジックこそ、分割し、テスト可能な形（純粋関数化など）にする必要があります。 |
