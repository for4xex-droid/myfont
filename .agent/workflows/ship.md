# /ship - 本番環境への出荷とロールアウト制御

安心・安全に出荷する。デプロイメントを単なる「反映作業」ではなく、「可逆的で、監視可能で、段階的なロールアウト」として計画・実行するための最上位ワークフロー。

## 🎯 目的
システムダウンタイムを防ぎ、モニタリング可能な状態で本番環境へ安全に機能を解き放つこと。

## 🔄 実行プロセス

### Step 1: Pre-launch チェックリスト
以下の全品質ゲートが「Green」であることを確認する。

- **Code Quality**: `cargo check --workspace --tests`, `(cd apps/management-console && npm run lint)`, Unit/E2E テストがALL GREEN。不要な `console.log` やTODOの残存なし。
- **Security**: シークレット漏洩なし、依存関係にクリティカルな脆弱性なし（`npm audit` / `cargo audit`）。認証・認可のバリデーション実装済み。
- **Performance**: N+1クエリなし。コアウェビタルやAPIレスポンスタイムの基本要件充足。
- **Infrastructure**: 本番用環境変数準備、DBマイグレーション準備完了。
- **Documentation**: CHANGELOG, README, ADRの更新完了。仕様書と実装の乖離ゼロ。

### Step 2: リリース・プリフライト の確認
衛生チェックと機密情報漏洩を防ぐために、以下のアシスタントワークフローがクリアされているか確認する。
- 必須: `/release-preflight` を実行し、すべてのチェックがパスしていること。

### Step 3: ロールアウト戦略と Feature Flag
機能の性質応じて、以下のどのフェーズでデプロイするかを定義する。

1. **Deploy with flag OFF**: コードは本番環境にあるがユーザーには非アクティブ
2. **Internal Beta**: 社内/特定チームのみ有効
3. **Canary Load**: 全体トラフィックの 5% のみに有効
4. **Gradual Rollout**: 25% → 50% → 100%

*(※Feature Flagには必ずオーナと有効期限を設定し、ロールアウト完了後2週間以内にFlagコードを削除すること)*

### Step 4: ロールバックプランのドキュメント化
必ず「失敗時のトリガー」と「復旧手順」をADRやIssue側に定義しておく。

- ロールバックトリガー:
  - エラー率 > ベースラインの2倍
  - P95 レイテンシ > 許容値の50%増
  - クリティカルなセキュリティインシデント報告
- アクション例:
  - Feature Flag の即時無効化（1分以内）
  - 対象コミットの `git revert` と再デプロイ（5分以内）
  - DBマイグレーションが存在する場合のダウングレード手順

## 📊 Rollout Decision Thresholds (意思決定マトリクス)

| メトリクス | Advance (🟢 進行) | Hold (🟡 調査・停止) | Rollback (🔴 即時撤退) |
|------------|----------------|--------------------|------------------------|
| **エラー率** | ベースライン±10%以内 | ベースラインから10-100%増加 | ベースラインの2倍超 |
| **P95 レイテンシ** | ±20%以内 | 20-50%増加 | 50%以上の増加 |
| **クライアントエラー** | 新規エラーなし | セッションの0.1%未満で新規エラー | セッションの0.1%以上で新規エラー |
| **ビジネス数値** | ニュートラル/ポジティブ | 5%未満の低下 (ノイズの可能性) | 5%以上の明確な低下 |

## 🛑 共通の言い訳 (Anti-rationalization)

| エージェント(AI)のよくある言い訳 | 現実 (Reality) |
|----------------------|----------------|
| 「ステージングで動いたので本番でも動きます」 | 本番はデータ量、トラフィック、エッジケースが全く異なります。デプロイ後も必ず監視を。 |
| 「単純な変更なのでFeature Flagは不要です」 | 「単純な変更」こそがシステムを落とします。キルスイッチ(Feature Flag)は常に用意すべきです。 |
| 「監視メトリクスは後で追加します」 | リリース直後が最も予測不能なエラーが起きます。見えないものはデバッグできません。 |
| 「ロールバックは失敗を認めることです」 | 安全なロールバックは責任あるエンジニアリングです。壊れた機能を放置することこそが「失敗」です。 |
| 「金曜の夕方ですが、出荷しましょう！」 | 深刻な緊急パッチ以外、翌日(休日)の対応負荷を考慮して見送るのがプロフェッショナルです。 |
